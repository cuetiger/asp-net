### 2.1 .NET 岗位常见面试题（50+道精选）

#### C# 语言基础（10题）

**Q1: 值类型(Value Type)和引用类型(Reference Type)的区别？**
```
值类型：struct, enum, bool, int, double等 → 存储在栈上，拷贝时复制整个数据
引用类型：class, interface, delegate, string, object等 → 存储在堆上，拷贝时复制引用

注意：string是特殊的引用类型（不可变性）
装箱(Boxing)：值类型→引用类型（有性能开销）
拆箱(Unboxing)：引用类型→值类型（需要类型匹配，否则异常）
```

**Q2: delegate、event、Action、Func的区别？**
```
delegate: 自定义委托类型声明
event: 基于委托的事件封装（+=/-=操作，外部不能直接触发）
Action<T>: 无返回值的泛型委托（最多16个参数）
Func<T,TResult>: 有返回值的泛型委托
Predicate<T>: 返回bool的泛型委托（常用于过滤条件）
```

**Q3: async/await的工作原理？**
```
async方法编译成状态机(State Machine)
await之前的代码同步执行
遇到await时：
  1. 如果任务已完成，继续同步执行
  2. 如果任务未完成，注册回调，将控制权返回给调用者
  3. 任务完成后，由SynchronizationContext（或ThreadPool）恢复执行
  4. 继续执行await之后的代码

死锁风险：在同步上下文中用.Result/.Wait()等待异步方法
解决方案：.ConfigureAwait(false) 或 全链路异步
```

**Q4: LINQ的Deferred Execution（延迟执行）vs Immediate Execution（立即执行）？**
```
延迟执行：var query = list.Where(x => x > 5); // 此时未执行查询
立即执行：var result = query.ToList(); // 此刻执行查询

延迟执行的LINQ操作符：Where/Select/OrderBy/Take/Skip...
触发立即执行的操作符：ToList()/ToArray()/Count()/First()/Max()...

优势：可以组合构建复杂查询，只在最后执行一次
风险：多次枚举导致重复计算（应使用ToList()缓存）
```

**Q5: 什么是闭包(Closure)？有什么陷阱？**
```
闭包：匿名函数（lambda/匿名方法）捕获外部变量
陷阱：循环中的闭包变量捕获的是引用而非值的副本

// 错误示例
for (int i = 0; i < 5; i++)
{
    actions.Add(() => Console.WriteLine(i)); // 所有action都打印5
}

// 正确做法
for (int i = 0; i < 5; i++)
{
    int copy = i; // 创建局部副本
    actions.Add(() => Console.WriteLine(copy)); // 正确打印0-4
}
```

#### ASP.NET Core 核心知识（15题）

**Q6: ASP.NET Core的请求处理管道是什么？**
```
HTTP Request → Server (Kestrel/IIS)
  → Middleware 1 (e.g., Exception Handler)
  → Middleware 2 (e.g., HTTPS Redirection)
  → Middleware 3 (e.g., Static Files)
  → Middleware 4 (e.g., Routing)
  → Middleware 5 (e.g., Authentication)
  → Middleware 6 (e.g., Authorization)
  → Middleware N (e.g., Endpoint/MVC)
  → HTTP Response

每个Middleware:
  - 可以决定是否传递给下一个(next.Invoke())
  - 可以在next之前和之后添加逻辑
  - 可以短路管道（不调用next）
  - 顺序很重要！
```

**Q7: 依赖注入(DI)的三种服务生命周期？**
```
Transient（瞬态）：每次请求创建新实例 → 适用于无状态服务
Scoped（作用域）：每个Scope（通常是一个HTTP请求）共享同一实例 → 适用于EF DbContext
Singleton（单例）：整个应用生命周期只有一个实例 → 必须线程安全

常见错误：
❌ 在Singleton中注入Scoped服务 → 会抛出异常
✅ 使用IScopeFactory< T > 或 IServiceProvider.CreateScope() 解决

AddScoped<IService, Service>() // 接口和实现分开注册
```

**Q8: MVC中过滤器(Filter)的执行顺序？**
```
全局过滤器(Global Filters) → 控制器过滤器(Controller Filters) → 动作过滤器(Action Filters)

执行流程（以AuthorizationFilter为例）:
OnAuthorization (Global) → OnAuthorization (Controller) → OnAuthorization (Action)

异常过滤器(Exception Filter)是反向执行的（内层先执行）
资源过滤器(Resource Filter)最先执行最后退出

自定义过滤器特性：
[AttributeUsage(AttributeTargets.Class | AttributeTargets.Method)]
public class MyFilterAttribute : ActionFilterAttribute { ... }
```

**Q9: 中间件(Middleware)和过滤器(Filter)的区别？**
```
                    Middleware                      Filter
作用范围:          整个管道                        Controller/Action级别
使用方式:          Use/Mapp/Run扩展方法            特性(Attribute)标注
访问HttpContext:   直接访问                       通过ActionExecutingContext
适用场景:          跨切点关注点(日志/认证/错误)     业务逻辑层面的处理
性能开销:          较轻                           较重（MVC上下文创建）
```

#### Entity Framework Core（8题）

**Q10: Change Tracker的工作原理？**
```
Entity Framework Core通过Change Tracker追踪实体的状态变化:

状态类型:
- Added: 新增实体（Insert）
- Unchanged: 未修改（不需要Update）
- Modified: 已修改（Update）
- Deleted: 已删除（Delete）
- Detached: 未被追踪

工作流程:
1. 从DB查询的实体自动被追踪（Unchanged状态）
2. 修改属性后变为Modified状态
3. 调用SaveChanges()时：
   - 生成对应的INSERT/UPDATE/DELETE语句
   - 按照正确的顺序执行（考虑外键约束）
4. SaveChanges后状态重置为Unchanged

性能提示:
- AsNoTracking() 用于只读查询（不追踪，更快）
- Attach() 手动将Detached实体附加到上下文
```

**Q11: N+1问题及解决方案？**
```
N+1问题场景:
var orders = context.Orders.ToList();           // 第1次查询
foreach(var order in orders)
{
    var customer = order.Customer;              // 触发N次额外查询！
}

解决方案:
1. Include() 急切加载（JOIN查询）
   context.Orders.Include(o => o.Customer).ToList();

2. ThenInclude() 多层加载
   context.Orders.Include(o => o.Items)
                     .ThenInclude(i => i.Product).ToList();

3. Select() 投影（只查需要的字段，最高效）
   context.Orders.Select(o => new {
       o.Id,
       CustomerName = o.Customer.Name,
       ItemCount = o.Items.Count
   }).ToList();

4. Split Query (.NET 5+) 将一个大JOIN拆分为多个小查询
   .AsSplitQuery()
```

#### 设计模式与架构（8题）

**Q12: 依赖倒置原则(DIP)的实现方式？**
```
DIP: 高层模块不应依赖低层模块，两者都应依赖抽象

实现方式:
1. 构造函数注入（推荐）
   public class OrderService
   {
       private readonly IRepository<Order> _repo;
       public OrderService(IRepository<Order> repo) { _repo = repo; }
   }

2. 属性注入
   [FromServices]
   public ILogger<OrderService> Logger { get; set; }

3. 方法注入
   public void Process([FromServices] IEmailService email) { ... }

4. 服务定位器（不推荐，反模式）
   var service = provider.GetService<IService>();
```

**Q13: Repository Pattern 和 Unit of Work？**
```
Repository Pattern:
- 封装数据访问逻辑，提供集合式的接口
- 使业务层不依赖于具体的数据访问技术
public interface IRepository<T> where T : class
{
    Task<T> GetByIdAsync(int id);
    Task<IEnumerable<T>> GetAllAsync();
    Task<IEnumerable<T>> FindAsync(Expression<Func<T, bool>> predicate);
    Task AddAsync(T entity);
    void Update(T entity);
    void Delete(T entity);
}

Unit of Work:
- 管理多个Repository的事务边界
- 确保多个操作在同一事务中原子性提交/回滚
public interface IUnitOfWork : IDisposable
{
    IRepository<T> GetRepository<T>();
    Task<int> SaveChangesAsync();
}
```

#### 数据库与性能（5题）

**Q14: SQL Server索引的类型和选择？**
```
聚集索引(Clustered Index):
- 数据按索引顺序物理存储
- 一个表只能有一个（通常是主键）
- 范围查询效率高

非聚集索引(Non-clustered Index):
- 独立于数据的索引结构（B+树）
- 包含索引列+聚集键（或指向堆的指针）
- 一个表可以有多个

包含索引(Included Columns):
- 非键列存储在叶子节点
- 避免回表查询（Covering Index）

选择原则:
- WHERE/JOIN/ORDER BY/GROUP BY的列
- 选择性高（唯一值多）的列优先建索引
- 避免过度索引（影响写入性能）
```

**Q15: CI/CD流水线的基本组成？**
```
CI (Continuous Integration):
├── 代码提交触发（Push/PR）
├── 编译(Build)
├── 单元测试(Unit Test)
├── 代码质量扫描(SonarQube)
└── 打包(Package: Docker Image/NuGet)

CD (Continuous Delivery/Deployment):
├── 部署到开发环境(Dev) → 自动
├── 部署到测试环境(QA/Staging) → 自动或手动审批
├── 集成测试(E2E Test)
├── 性能测试(Load Test)
└── 部署到生产环境(Prod) → 手动审批 + 蓝绿/金丝雀发布

常用工具:
- GitHub Actions / Azure DevOps Pipelines / Jenkins
- Docker + Kubernetes
- Terraform / ARM Templates (基础设施即代码)
```

*(其余3题：Docker多阶段构建 / Kubernetes基本概念 / 监控告警体系)*

### 2.2 项目经验包装方法

**原则：STAR法则**

```
S - Situation（情境）：项目背景和面临的挑战
T - Task（任务）：你承担的具体责任
A - Action（行动）：你采取的关键行动和技术方案
R - Result（结果）：量化的成果和价值
```

**好的项目描述示例**：

> ❌ 弱描述："参与了电商后台管理系统开发，使用了ASP.NET Core和EF Core。"

> ✅ 强描述："作为后端负责人，主导了电商订单系统的重构（Situation）。原系统基于.NET Framework单体架构，下单接口响应时间超过2秒，无法支撑双11流量峰值（Task）。我采用领域驱动设计(DDD)将订单模块拆分为独立的微服务，引入RabbitMQ实现异步解耦，使用Redis缓存热点商品信息，并将数据库从SQL Server迁移至PostgreSQL以降低成本（Action）。重构后下单接口P99延迟从2000ms降至150ms，系统成功支撑了日均50万订单的处理量，服务器成本降低了40%（Result）。"

**包装要点**：
- 用数字说话（性能提升百分比、处理量、成本节约）
- 突出你的角色（主导/独立负责/核心成员）
- 体现技术深度（不是罗列技术名词，而是说明为什么选它）
- 展示解决问题的能力（遇到的挑战和如何克服）

### 5.2 开源贡献

**开源贡献的价值层级**：

```
Level 1: 用户（User）
└── 使用开源项目，反馈Bug和功能请求

Level 2: 文档贡献者（Documenter）
└── 改进文档、翻译文档、修复拼写错误
    → 最佳的入门方式！

Level 3: Bug Fixer（问题修复者）
└── 复现并修复已报告的Bug
    → 从"good first issue"开始

Level 4: Feature Implementer（功能实现者）
└── 实现新功能或增强
    → 需要对项目有较深的理解

Level 5: Maintainer / Committer（维护者）
└── 有写入权限，负责代码审查和发布
    → 长期投入后的信任建立

Level 6: Creator / BDFL（创建者）
└── 发起和维护自己的开源项目
    → 最大的影响力和成就感
```

**从零开始贡献开源的步骤**：

```bash
Week 1: 选择项目和Issue
├── 浏览感兴趣的项目的GitHub仓库
├── 查看"Issues"标签页
├── 筛选 "good first issue" / "help wanted"
├── 选择一个你能理解的Issue
└── 在Issue下留言表示你想尝试解决

Week 2: 本地开发和修复
├── Fork仓库到你的账号
├── Clone Fork到本地
├── 创建新分支 git checkout -b fix/issue-number-description
├── 编写代码修复问题
├── 添加测试（如果有测试套件的话）
├── 本地验证修复有效
└── Commit并Push到你的Fork

Week 3: 提交Pull Request
├── 在GitHub上创建PR
├── 写清楚PR描述（What/Why/How）
├── 引用原始Issue编号（Fixes #123）
├── 回应Maintainer的Review意见
├── 根据反馈修改代码
└── PR合并！🎉
```

## 六、薪资谈判技巧

### 6.1 谈判前的准备

**了解市场行情**：
- 使用以下资源调研薪资：
  - Boss直聘/拉勾的岗位薪资范围
  - Offershow / 看准网的薪酬报告
  - Levels.fyi（国际岗位）
  - 同行朋友的真实薪资（最准确的一手信息）

**明确你的底线**：
- 最低可接受薪资（低于此不接受）
- 期望薪资（你的目标）
- 理想薪资（如果运气好可以争取到的）

**准备谈判筹码**：
- 多个Offer在手（最有力的筹码）
- 稀缺技能（如Azure/Kubernetes/AI+.NET）
- 特殊成就（开源项目、知名演讲、技术博客）
- 竞争对手的Offer letter

### 6.2 谈判策略

**时机选择**：
- ✅ 收到书面Offer之后
- ✅ HR电话通知你通过面试时
- ❌ 面试过程中（显得太急功近利）
- ❌ 第一轮口头报价时（先表示感谢，要求书面确认）

**谈判话术模板**：

```
感谢您提供的Offer！我对这个机会和团队非常感兴趣。
经过仔细考虑，基于我的[X年经验]和在[Y领域的专业技能]，
以及当前市场对于[Z技能]的需求，我希望薪资能够调整到[期望数字]。

我相信我的加入可以为团队带来[A/B/C方面的价值]，
我也非常有信心在这个岗位上取得出色的成绩。
希望能找到一个双方都满意的结果。
```

**谈判要点**：
1. **不要接受第一次报价**（除非远超预期）
2. **给出合理理由**（市场行情、个人价值、特殊技能）
3. **整体薪酬包视角**（不只是月薪，还包括奖金、股票、福利、假期）
4. **保持专业和友善**（这不是对抗，而是协商）
5. **知道何时停止**（如果对方已经让步到极限，见好就收）

**除了薪资还可以谈什么**：
- 年终奖（几个月？是否有保底？）
- 股票/期权（数量、归属期、行权价格）
- 签字费（Signing Bonus，跳槽时常见）
- 工作方式（远程天数、弹性工作时间）
- 培训预算（参加会议、购买课程的费用报销）
- 职级Title（Senior vs Staff vs Principal）
- 入职日期（给自己留足交接时间）

## 七、工作与学习平衡

### 7.1 在职提升策略

**现实挑战**：全职工作后，可用于学习的时间大幅减少。如何在繁忙的工作之余持续成长？

**时间审计**（先了解时间去哪了）：

```
典型的一天（工作日）：
├── 通勤：1-2小时 → 🎧 听播客/技术音频的最佳时间
├── 工作：8-9小时 → 💻 工作中学（选择有挑战性的任务）
├── 午休：1小时 → 📖 读技术文章/看短视频教程
├── 晚餐+休息：2小时 → 👨‍👩‍👧 家庭时间（不要牺牲）
├── 学习时间：1-2小时 → 📝 深度学习（固定时间段）
└── 睡眠：7-8小时 → 😴 不要压缩睡眠！

周末（两天）：
├── 周六：4-6小时 → 🛠️ 动手实践（项目/开源/实验）
├── 周日：2-3小时 → 📝 总结复习 + 下周计划
└── 休息娱乐：保持可持续性
```

**每周可用的有效学习时间**：
- 工作日：约1.5小时/天 × 5天 = 7.5小时
- 周末：约6-8小时
- **总计：约13-15小时/周**（足够完成很多学习目标！）

**高效利用碎片时间的策略**：

| 时间段 | 时长 | 推荐活动 | 工具 |
|--------|------|----------|------|
| **通勤（来回）** | 1-2h | 技术播客/有声书 | Podcast App / Audible |
| **排队/等候** | 5-15min | 刷技术Twitter/阅读Newsletter | 手机 |
| **午休** | 30-60min | 看技术短视频/读短文章 | YouTube / 掘金 |
| **睡前** | 15-30min | 回顾当天所学/计划明天 | 笔记App |
| **周末早晨** | 2-3h | 深度学习（整块时间） | 电脑 |

### 7.2 利用工作来学习（最高效的方式）

**主动选择有挑战性的任务**：
- 主动请缨做新技术预研
- 申请负责有技术难度的模块
- 争取参加架构设计讨论
- 志愿修复历史遗留的难题

**在工作中实践新学到的知识**：
- 学了Docker？提议将一个服务容器化
- 学了Redis？找一个合适的功能引入缓存
- 学了单元测试？给老代码补充测试
- 学了Clean Architecture？在新模块中实践

**向身边的专家学习**：
- 团队里的Senior/Staff Engineer是你的免费导师
- Code Review是最直接的学习机会（仔细看别人的代码）
- 午餐时聊聊技术话题
- 不懂就问（但先自己研究过）

### 7.3 避免倦怠的策略

**警告信号**：
- 对技术失去好奇心和热情
- 每天上班感到身心俱疲
- 学习变成负担而不是享受
- 持续失眠或焦虑
- 对简单的任务也感到困难

**预防和恢复**：

```
预防措施：
├── 设定可持续的学习节奏（不要过度）
├── 保证充足的睡眠和运动
├── 培养技术之外的兴趣爱好
├── 定期休假（真正的断联）
└── 与家人朋友保持高质量相处时间

恢复措施：
├── 暂停高强度学习1-2周
├── 做一些创造性但不"有用"的副项目
├── 反思当前的职业方向是否正确
├── 寻求心理咨询（如果需要）
└── 考虑换环境（有时换个团队就能恢复）
```

## 八、总结与行动计划

### 8.1 职业发展阶段自查表

**当前你在哪个阶段？**

| 维度 | Junior | Mid | Senior | Staff+ |
|------|--------|-----|--------|--------|
| **技术深度** | 能用 | 熟悉 | 精通 | 行业领先 |
| **技术广度** | 知晓 | 了解 | 掌握 | 融会贯通 |
| **独立性** | 需指导 | 独立负责 | 独当一面 | 自主决策 |
| **影响力** | 个人 | 小组 | 团队 | 跨团队/行业 |
| **收入水平** | 入门级 | 中等 | 中高 | 高/很高 |

### 8.2 未来90天行动计划

**第一个月：基础夯实**
- [ ] 完成当前工作中的核心技能强化（选定1项深入学习）
- [ ] 更新简历和GitHub Profile
- [ ] 开始写第一篇（或恢复）技术博客
- [ ] 建立/整理个人知识库（Obsidian）

**第二个月：影响力启动**
- [ ] 在团队内做一次技术分享（15-30分钟）
- [ ] 为一个开源项目提交第一个PR（哪怕只是修文档）
- [ ] 参加1次线下或线上的技术Meetup
- [ ] 完成1本书的阅读（或等量的课程学习）

**第三个月：职业推进**
- [ ] 评估当前职位的满意度和发展空间
- [ ] 如果考虑跳槽：开始关注市场机会，更新Boss直聘资料
- [ ] 如果考虑内部晋升：找Manager聊职业发展规划
- [ ] 制定下一季度的学习和成长目标

### 8.3 给不同阶段的寄语

**致初级开发者**：
> "不要急于求成。你现在最重要的任务是打好坚实的基础。每一个你觉得'太简单'的概念，未来都会成为你构建复杂系统的基石。保持好奇心，多问为什么，享受学习的乐趣。"

**致中级开发者**：
> "这是成长最快的阶段，也是最危险的瓶颈期。你可能感觉自己什么都懂一点但又什么都不精。这是正常的！选择一个方向深入下去（比如成为'EF Core专家'或'微服务架构师'），同时保持广度的视野。开始建立你的个人品牌，让行业知道你的存在。"

**致高级开发者**：
> "你已经证明了你的技术能力。现在的挑战是如何放大你的影响力——通过带领团队、做技术决策、影响整个组织甚至行业。不要只做一个'高级码农'，要成为一个能够解决复杂问题、引领技术方向的'技术领袖'。"

**致所有.NET开发者**：
> ".NET生态从未如此强大和充满活力。从云端到边缘，从Web到AI，从桌面到移动，.NET无处不在。你选择的这条路，前景光明。保持学习，保持热情，保持连接。祝你在技术的道路上走得更远、更高！"
