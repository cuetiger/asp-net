# Todo应用 - 需求分析文档

## 一、项目背景和目标

### 1.1 为什么做这个项目？

在软件开发学习过程中，**Todo应用（待办事项管理）**是最经典且实用的入门项目。它涵盖了Web开发的核心知识点，同时具有实际应用价值。

**选择这个项目的原因：**

- **涵盖核心概念**：CRUD操作、数据库交互、表单验证、用户界面设计
- **复杂度适中**：不会太简单失去学习价值，也不会太复杂让初学者望而却步
- **实用性强**：可以真正使用这个应用来管理工作任务
- **可扩展性好**：从MVP版本开始，逐步添加高级功能

### 1.2 学什么？

通过完成这个项目，你将掌握：

| 技术领域 | 具体内容 |
|---------|---------|
| **ASP.NET Core MVC** | 控制器、视图、路由、模型绑定 |
| **Entity Framework Core** | Code First迁移、LINQ查询、数据上下文 |
| **SQL Server** | 数据库设计、表关系、索引优化 |
| **Razor视图** | HTML辅助方法、布局页、分部视图 |
| **表单验证** | 数据注解、客户端验证、自定义验证器 |
| **分层架构** | Repository模式、Service层、依赖注入 |
| **前端技术** | Bootstrap 5、jQuery、AJAX请求 |
| **测试实践** | 单元测试、xUnit框架、Moq模拟 |

### 1.3 项目目标

构建一个功能完整、代码规范的待办事项管理系统，具备以下特点：

- ✅ 用户友好的界面
- ✅ 完整的CRUD功能
- ✅ 可靠的数据验证
- ✅ 良好的性能表现
- ✅ 清晰的代码结构

## 二、功能需求列表（用户故事格式）

### 2.1 核心功能（MVP版本必须实现）

#### 故事1：查看所有待办事项
**作为用户**，我希望能够**查看所有待办事项**，以便了解当前的工作任务。

**验收标准：**
- 显示待办事项列表，包含标题、状态、优先级、截止日期
- 列表支持分页显示（每页10条）
- 默认按创建时间倒序排列
- 已完成的任务有明显的视觉标识

**优先级：** P0（必须有）

---

#### 故事2：添加新的待办事项
**作为用户**，我希望能够**添加新的待办事项**，以便记录需要完成的工作。

**验收标准：**
- 提供创建表单页面
- 必填字段：标题
- 可选字段：描述、优先级、截止日期
- 标题长度限制在200个字符以内
- 添加成功后返回列表页并显示成功提示
- 自动记录创建时间

**优先级：** P0（必须有）

---

#### 故事3：编辑已有的待办事项
**作为用户**，我希望能够**编辑已有的待办事项**，以便修改任务信息。

**验收标准：**
- 提供编辑表单页面，预填充现有数据
- 可以修改所有字段（标题、描述、优先级、截止日期）
- 编辑成功后更新修改时间
- 支持并发控制（防止多人同时编辑导致数据丢失）

**优先级：** P0（必须有）

---

#### 故事4：删除待办事项
**作为用户**，我希望能够**删除待办事项**，以便移除不再需要的任务。

**验收标准：**
- 删除前显示确认对话框
- 删除成功后从列表中移除并显示提示
- 支持软删除（可选，标记为已删除而非物理删除）

**优先级：** P0（必须有）

---

#### 故事5：标记完成状态
**作为用户**，我希望能够**标记待办事项为完成状态**，以便跟踪任务进度。

**验收标准：**
- 提供快速切换完成状态的按钮/复选框
- 状态变更即时生效（无需进入编辑页）
- 完成的任务在列表中有明显区分（如删除线、灰色背景）
- 记录完成时间（可选）

**优先级：** P0（必须有）

---

#### 故事6：按状态筛选
**作为用户**，我希望能够**按状态筛选待办事项**，以便快速找到特定类型的任务。

**验收标准：**
- 提供筛选下拉框或标签页
- 筛选选项：全部 / 未完成 / 已完成
- 筛选结果与搜索、分页功能协同工作
- 当前筛选状态清晰可见

**优先级：** P1（应该有）

---

#### 故事7：搜索待办事项
**作为用户**，我希望能够**搜索待办事项（按标题或描述）**，以便快速定位特定任务。

**验收标准：**
- 提供搜索输入框
- 支持模糊匹配（包含关键词即可）
- 搜索范围覆盖标题和描述字段
- 实时搜索或回车触发搜索
- 搜索结果高亮显示关键词
- 清空搜索框时恢复完整列表

**优先级：** P1（应该有）

---

### 2.2 增强功能（V1.1版本考虑）

#### 故事8：设置优先级（可选）
**作为用户**，我希望能够**设置待办事项的优先级**，以便区分任务的重要程度。

**验收标准：**
- 提供3个级别：普通（默认）、重要、紧急
- 不同优先级用不同颜色或图标标识
- 支持按优先级排序和筛选
- 高优先级任务在列表中突出显示

**优先级：** P2（可以有）

---

#### 故事9：设置截止日期（可选）
**作为用户**，我希望能够**设置截止日期**，以便管理任务的时间安排。

**验收标准：**
- 提供日期选择器控件
- 截止日期不能早于当前时间（验证规则）
- 即将到期（24小时内）的任务有警告提示
- 已过期任务用红色标识
- 支持按截止日期排序

**优先级：** P2（可以有）

## 三、非功能需求

### 3.1 性能要求

| 指标 | 要求 | 说明 |
|------|------|------|
| **响应时间** | 页面加载 < 2秒 | 首屏渲染时间 |
| **查询性能** | 列表查询 < 500ms | 包含筛选和分页 |
| **并发能力** | 支持100+同时在线用户 | 基本并发访问 |
| **数据库连接** | 连接池大小合理配置 | 避免连接泄漏 |

**性能优化策略：**
- 使用`AsNoTracking()`进行只读查询
- 列表页使用Select投影减少数据传输
- 合理设置数据库索引
- 启用响应压缩中间件

### 3.2 安全要求

| 方面 | 要求 |
|------|------|
| **输入验证** | 所有用户输入必须经过服务端验证 |
| **SQL注入防护** | 使用参数化查询（EF Core自动处理） |
| **XSS防护** | 对输出进行HTML编码（Razor自动处理） |
| **CSRF防护** | 启用防伪令牌验证 |
| **错误信息** | 不暴露敏感的系统异常信息 |

### 3.3 可用性要求

| 方面 | 要求 |
|------|------|
| **浏览器兼容** | Chrome、Firefox、Edge最新两个版本 |
| **响应式设计** | 支持桌面端（>1024px）和平板（768-1024px） |
| **用户体验** | 操作反馈及时（Loading状态、成功/错误提示） |
| **错误恢复** | 表单提交失败后保留用户已输入的数据 |
| **无障碍性** | 基本的ARIA标签支持 |

### 3.4 可维护性要求

- 代码遵循SOLID原则
- 分层架构清晰（Controller → Service → Repository）
- 配置与代码分离
- 充分的代码注释
- 统一的命名规范

## 四、技术选型说明

### 4.1 技术栈总览

```
┌─────────────────────────────────────────┐
│              前端展示层                   │
│    Bootstrap 5 + jQuery + Razor Views   │
├─────────────────────────────────────────┤
│            应用逻辑层                    │
│     ASP.NET Core MVC Controllers        │
├─────────────────────────────────────────┤
│             业务逻辑层                   │
│          Service Layer (C#)             │
├─────────────────────────────────────────┤
│            数据访问层                    │
│    Entity Framework Core + LINQ         │
├─────────────────────────────────────────┤
│              数据存储                    │
│          SQL Server (LocalDB)           │
└─────────────────────────────────────────┘
```

### 4.2 为什么选择 ASP.NET Core MVC？

**优势对比：**

| 特性 | ASP.NET Core MVC | 其他选项（如Node.js） |
|------|------------------|---------------------|
| **类型安全** | C#强类型，编译时检查 | JavaScript动态类型 |
| **性能** | 高性能，异步原生支持 | 需要额外配置 |
| **开发工具** | Visual Studio强大支持 | 工具链相对较弱 |
| **生态系统** | NuGet包丰富 | npm生态庞大但质量参差 |
| **学习曲线** | 结构化，适合团队协作 | 灵活但容易混乱 |
| **企业采用** | 广泛用于企业级项目 | 更多用于初创公司 |

**选择理由：**

1. **跨平台支持**：可在Windows、Linux、macOS上运行
2. **高性能**：相比传统ASP.NET提升2-3倍性能
3. **现代化架构**：内置依赖注入、中间件管道
4. **开源免费**：MIT许可证，无商业限制
5. **社区活跃**：微软官方持续维护，文档完善

### 4.3 为什么选择 Entity Framework Core？

**ORM框架对比：**

| 特性 | EF Core | Dapper | ADO.NET |
|------|---------|--------|---------|
| **开发效率** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ |
| **性能** | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **学习曲线** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐ |
| **灵活性** | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **迁移支持** | ⭐⭐⭐⭐⭐ | ❌ | ❌ |

**选择理由：**

1. **Code First开发**：先定义实体类，自动生成数据库
2. **LINQ集成**：类型安全的查询语法，编译时检查
3. **变更追踪**：自动检测实体变化，简化更新操作
4. **迁移系统**：版本化管理数据库结构变更
5. **官方支持**：微软官方ORM，与.NET生态深度集成

### 4.4 为什么选择 SQL Server？

**数据库选型：**

| 数据库 | 适用场景 | 本项目适用度 |
|--------|---------|-------------|
| **SQL Server (LocalDB)** | 开发环境、小型应用 | ⭐⭐⭐⭐⭐ |
| SQLite | 嵌入式应用、移动端 | ⭐⭐⭐ |
| PostgreSQL | 开源项目、复杂查询 | ⭐⭐⭐⭐ |
| MySQL | Web应用、成本敏感 | ⭐⭐⭐⭐ |

**选择理由：**

1. **LocalDB轻量**：无需安装完整SQL Server，适合开发
2. **与EF Core完美配合**：官方提供程序包，功能完整
3. **T-SQL熟悉度高**：如果学过SQL Server，上手快
4. **工具支持好**：SSMS、Visual Studio集成
5. **生产可升级**：后期可无缝迁移到完整版SQL Server

|------|------|------|

| ASP.NET Core | 8.0 | MVC框架 |

## 七、风险和依赖

### 7.1 技术风险

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|---------|
| EF Core性能问题 | 低 | 中 | 使用AsNoTracking、优化查询 |
| SQL Server LocalDB兼容性 | 低 | 低 | 提供SQLite备选方案 |
| Bootstrap版本冲突 | 低 | 低 | 使用CDN固定版本号 |
| 浏览器兼容性问题 | 中 | 低 | 主流浏览器测试 |

### 7.2 学习曲线风险

**可能遇到的困难：**

1. **依赖注入概念**：初次接触可能困惑
   - *解决方案*：先理解"为什么要DI"，再看具体用法

2. **async/await异步编程**：容易出错
   - *解决方案*：理解Task机制，避免死锁

3. **LINQ查询语法**：与SQL不同
   - *解决方案*：多做练习，对比SQL和LINQ

4. **Razor语法**：HTML和C#混合
   - *解决方案*：先掌握基础语法，再学高级特性

### 7.3 外部依赖

| 依赖项 | 版本 | 用途 | 备选方案 |
|--------|------|------|---------|
| .NET 8.0 SDK | 8.0.400+ | 运行时环境 | .NET 7.0（降级） |
| SQL Server LocalDB | 2022 | 数据库 | SQLite |
| NuGet包 | 最新稳定版 | 第三方库 | 锁定版本号 |
