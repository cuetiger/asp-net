> **目标读者**：需要进行技术决策、架构设计和代码组织的中高级开发者

## 问题1：MVC vs Razor Pages vs Blazor 如何选？

### 对比分析

| 特性 | MVC | Razor Pages | Blazor Server | Blazor WASM |
|------|-----|-------------|--------------|------------|
| 学习曲线 | 中等 | 低 | 中等 | 高 |
| SEO支持 | 需额外处理 | 原生支持 | 差 | 需预渲染 |
| 实时性 | 好（服务端渲染） | 好 | 极好 | 好（客户端） |
| 包体积 | 小 | 小 | 较大 | 大（需下载运行时） |
| 离线能力 | 无 | 无 | 无 | **有** |
| JavaScript交互 | 需要JS框架 | 需要JS框架 | C#即可 | 可互操作 |
| 适用场景 | 复杂API/多端 | 传统表单页 | 内部管理工具 | 交互式Web应用 |

### 选择建议

```
选择 MVC/Razor Pages 当：
- 需要 SEO 的内容网站
- 团队熟悉传统 Web 开发
- 对首屏性能要求高

选择 Blazor Server 当：
- 企业内部应用
- 需要实时功能（SignalR集成好）
- 团队以 C# 为主

选择 Blazor WASM 当：
- 需要 PWA / 离线能力
- 高度交互的 SPA 应用
- 可以接受较大的初始加载

混合方案：
- 主站用 Razor Pages/MVC（SEO）
- 管理后台用 Blazor Server
- 移动端 API 用 Blazor WASM 或纯 API
```

```csharp
    public async Task<IActionResult> Create([FromBody] CreateOrderDto dto)
    {
        // 100行的业务逻辑全在这里...
    }

// ✅ 瘦 Controller：只负责HTTP层关注点
[ApiController]
[Route("api/[controller]")]
public class OrdersController : ControllerBase
{
    private readonly IMediator _mediator;  // 使用Mediator模式

    public OrdersController(IMediator mediator)
    {
        _mediator = mediator;
    }

    /// <summary>
    /// 获取订单列表
    /// </summary>
    [HttpGet]
    [ProducesResponseType(typeof(PagedResult<OrderDto>), StatusCodes.Status200OK)]
    public async Task<ActionResult<PagedResult<OrderDto>>> GetOrders(
        [FromQuery] OrderFilterQuery query)
    {
        var result = await _mediator.Send(query);  // 发送查询到Handler
        return Ok(result);
    }

    [HttpPost]
    public async Task<ActionResult<OrderDto>> Create([FromBody] CreateOrderCommand command)
    {
        var result = await _mediator.Send(command);
        return CreatedAtAction(nameof(GetById), new { id = result.Id }, result);
    }
}
```

```csharp
// Handler：包含业务逻辑（可测试）
public class GetOrdersHandler : IRequestHandler<OrderFilterQuery, PagedResult<OrderDto>>
{
    private readonly IOrderRepository _orderRepo;
    private readonly IAuthorizationService _authz;

    public GetOrdersHandler(IOrderRepository orderRepo, IAuthorizationService authz)
    {
        _orderRepo = orderRepo;
        _authz = authz;
    }

    public async Task<PagedResult<OrderDto>> Handle(OrderFilterQuery request, CancellationToken ct)
    {
        // 权限验证
        var authorization = await _authz.AuthorizeAsync(
            User, "OrderReadPolicy");
        if (!authorization.Succeeded) throw new ForbiddenException();

        // 查询构建
        var query = _orderRepo.Queryable()
            .Include(o => o.User)
            .If(!string.IsNullOrEmpty(request.Keyword), 
                q => q.OrderNo.Contains(request.Keyword));

        // 执行查询
        var total = await query.CountAsync(ct);
        var items = await query
            .Skip((request.Page - 1) * request.PageSize)
            .Take(request.PageSize)
            .Select(o => OrderMapper.ToDto(o))
            .ToListAsync(ct);

        return new PagedResult<OrderDto>(total, items);
    }
}
```

## 问题3：循环依赖如何解决？

### 解决方案

```csharp
// ❌ 循环依赖示例
// A → B → C → A (循环!)

// 方案1：引入接口抽取公共行为
// A 和 C 都需要某个功能，将其提取为 IService
public interface ICommonService { void DoSomething(); }

// 方案2：使用事件解耦
// A 发布事件，C 订阅事件
public class ServiceA
{
    private readonly IMediator _mediator;
    
    public async Task DoWork()
    {
        await _mediator.Publish(new WorkCompletedEvent());
    }
}

public class ServiceC : INotificationHandler<WorkCompletedEvent>
{
    public async Task Handle(WorkCompletedEvent notification, CancellationToken ct)
    {
        // 响应事件
    }
}

// 方案3：延迟注入/Provider模式
public class ServiceA
{
    private readonly Func<IServiceC> _serviceCFactory;
    
    public ServiceA(Func<IServiceC> serviceCFactory)
    {
        _serviceCFactory = serviceCFactory;
    }
    
    public void Execute()
    {
        var serviceC = _serviceCFactory();  // 延迟获取
        serviceC.DoSomething();
    }
}

// 方案4：重新审视架构（根本解决）
// 如果A、B、C互相依赖，说明它们职责不清
// 应该合并或拆分为更细粒度的服务
```

## 问题4：什么时候该用微服务？

### 决策框架

```
应该考虑微服务当：
✅ 团队规模 > 50人，需要独立部署
✅ 不同模块技术栈差异大（.NET + Node.js + Python）
✅ 不同模块扩展需求差异大（订单服务10实例，用户服务2实例）
✅ 部署频率差异大（核心服务每周发布，报表服务每月发布）
✅ 故障隔离要求高（一个服务崩溃不影响全局）

不应该用微服务当：
❌ 团队 < 5人，单体足够
❌ 所有模块使用相同技术栈
❌ 模块间高度耦合（强事务一致性）
❌ 刚起步的初创项目（先做单体再拆分）
❌ 运维能力不足（微服务增加运维复杂度）
```

### 推荐演进路径

```
阶段1：单体架构（Monolith）
├── Controllers/
├── Services/
├── Data/
└── Infrastructure/

阶段2：模块化单体（Modular Monolith）
├── OrderModule/ (Controller + Service + Repo)
├── UserModule/
└── PaymentModule/

阶段3：按需拆分微服务（如果某模块成为瓶颈）
├── Order Service (独立部署)
├── User Service (仍在一起)
└── Payment Service (独立部署)

原则：不要为了微服务而微服务！
```

## 总结

| 架构决策 | 推荐场景 | 注意事项 |
|---------|----------|---------|
| MVC vs Razor Pages | 内容网站优先Razor Pages | 两者可共存 |
| Blazor | 内部工具/交互式应用 | WASM注意包大小 |
| 瘦Controller | MediatR/CQRS | 不要过度抽象 |
| 微服务 | 大团队/多技术栈 | 从单体开始演进 |
| DDD | 复杂业务领域 | 不要过度设计 |

**架构原则**：
1. **SOLID原则**是基础，但不要教条化
2. **简单优于复杂**：能用3个类解决的问题不要用10个
3. **分层清晰**：每层有明确职责
4. **易于测试**：好的架构让测试变得容易
5. **渐进式重构**：不要一次性重写
