# ASP.NET 性能问题排查指南

> **适用场景**：ASP.NET应用出现性能瓶颈、响应缓慢、资源占用过高等问题
>
> **目标读者**：需要进行性能分析、优化和调优的开发者和运维人员

---

## 问题1：首次加载慢（冷启动/JIT编译）

### 问题描述
应用首次启动或首次访问某个API时非常慢，后续请求正常。

### 原因分析
- JIT（Just-In-Time）编译：首次执行方法时需要编译为机器码
- 程序集加载：首次引用外部库时需要加载
- 数据库连接池预热：首次建立连接较慢
- 依赖注入容器初始化：Singleton服务初始化开销

### 解决方案

```csharp
// 方案1：使用ReadyToRun (Crossgen) 预编译
# 发布时启用：
dotnet publish -c Release -r win-x64 --self-contained true -p:PublishReadyToRun=true

# 或在.csproj中配置：
<PropertyGroup>
    <PublishReadyToRun>true</PublishReadyToRun>
</PropertyGroup>

// 方案2：启动时预热关键路径
public class StartupWarmupService : IHostedService
{
    private readonly IServiceProvider _services;

    public async Task StartAsync(CancellationToken ct)
    {
        // 预热数据库连接
        using var scope = _services.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        await db.Database.CanConnectAsync(ct);

        // 预热常用服务
        var cache = scope.ServiceProvider.GetRequiredService<IMemoryCache>();
        cache.Set("warmup", DateTime.UtcNow);

        Console.WriteLine("Application warmup completed.");
    }

    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}

// 方案3：使用Startup Hook (.NET 8)
// 在 .runtimeconfig.json 中配置
/*
{
  "startupHook": ["MyApp.WarmupHook, MyApp"]
}
*/
```

## 问题2：API 响应慢的排查步骤

### 排查清单

```
1. 测量实际耗时 → 确认是网络还是服务器慢
   curl -w "@\n时间总耗: %{time_total}s\n" http://localhost:5000/api/users

2. 检查日志 → 找到慢操作
   查看EF Core日志中的SQL执行时间

3. 使用MiniProfiler → 可视化请求生命周期
   dotnet add package MiniProfiler.AspNetCore.Mvc

4. 分析SQL执行计划 → 是否缺少索引
   SET STATISTICS IO ON; SET STATISTICS TIME ON;

5. 检查N+1查询 → Include/Select优化
   启用EF Core敏感数据日志查看所有SQL
```

## 问题3：内存持续增长（内存泄漏定位）

### 工具和方法

```bash
# 1. 实时监控
dotnet-counters monitor --counters System.Runtime --process-id <PID>

# 关键指标：
# - Working Set: 物理内存
# - Gen 0/1/2 Collections: GC频率
# - Allocation Rate: 分配速率
# - GC Heap Size: 托管堆大小

# 2. 生成Dump文件
dotnet-dump collect -p <PID> -o dump.dmp

# 3. 分析Dump
dotnet-dump analyze dump.dmp
> dumpheap -stat          # 堆统计
> gcroot <address>       # 引用链
> heapstat               # 类型分布
```

### 常见泄漏模式及修复

| 泄漏模式 | 示例代码 | 修复方式 |
|---------|---------|---------|
| 事件未取消订阅 | `obj.Event += Handler` | 使用 `Disposable.Create` 包装 |
| 静态集合无限增 | `static List<T> cache` | 使用LRU缓存或ConcurrentDictionary |
| Timer未Dispose | `new Timer(...)` | 实现 `IDisposable` |
| DbContext未Dispose | 手动创建未using | 使用DI或IServiceScopeFactory |
| 大对象频繁分配 | `byte[1024*1024]` 循环中 | 使用ArrayPool或流式处理 |

## 问题4：CPU 使用率过高

### 定位热点方法

```bash
# Linux: perf
perf top -p <PID>

# Windows: PerfView / dotnet-trace
dotnet-trace collect --process-id <PID> --providers Microsoft-Diagnostics-Metrics

# 代码层面：使用BenchmarkDotNet
[MemoryDiagnoser]
[SimpleJob(launchCount: 5, warmupCount: 3)]
[BenchmarkCategory("String Operations")]
public class StringBenchmarks
{
    [Params(100, 1000, 10000)]
    public int Length { get; set; }

    [Benchmark]
    public string StringConcat()
    {
        string result = "";
        for (int i = 0; i < Length; i++)
            result += "x";
        return result;
    }

    [Benchmark]
    public StringBuilder StringBuilderTest()
    {
        var sb = new StringBuilder();
        for (int i = 0; i < Length; i++)
            sb.Append("x");
        return sb.ToString();
    }
}

# 运行基准测试
dotnet run -c Release --framework net8.0
```

## 问题5：GC 频繁触发

### 代回收分析

```csharp
// 监控GC事件
public class GCMonitor : EventListener
{
    protected override void EnableEvents()
    {
        EnableEvent("Microsoft-Windows-DotNETRuntime", EventLevel.Informational);
    }

    protected override void OnEventWritten(EventWrittenEventArgs e)
    {
        if (e.EventName == "GC/HeapStats")
        {
            var gen0 = (ulong)e.Payload["GenerationSize0"];
            var gen1 = (ulong)e.Payload["GenerationSize1"];
            var gen2 = (ulong)e.Payload["GenerationSize2"];
            var loh = (loh) e.Payload["LOHSize"];
            
            Console.WriteLine($"Gen0={gen1/1024}KB, Gen1={gen1/1024}KB, Gen2={gen2/1024}KB, LOH={loh/1024}KB");
        }
    }
}
```

**优化策略**:
- 减少短生命周期大对象的分配（避免进入Gen2）
- 使用 ArrayPool 复用缓冲区
- 对象池化（如 StringBuilderPool）
- 减少字符串拼接，使用StringBuilder

## 问题6：数据库查询慢

### SQL Server 执行计划分析

```sql
-- 开启实际执行计划
SET STATISTICS PROFILE ON;
GO

-- 执行你的查询
SELECT * FROM Orders WHERE CustomerId = @id AND OrderDate > @date;

-- 查看：
-- 1. Table Scan vs Index Seek（应该用索引）
-- 2. Key Lookup次数（是否需要包含列）
-- 3. 实际行数 vs 预估行数（统计信息过期？）
-- 4. Sort/Hash Match操作成本

-- 查找缺失索引建议
SELECT TOP 10 * FROM sys.dm_db_missing_index_details ORDER BY user_seeks + user_scans DESC;
```

## 问题7：并发量上去后服务崩溃

### 连接池和线程池调优

```csharp
// Program.cs
builder.Services.AddDbContextPool<AppDbContext>(options =>
    options.UseSqlServer(connectionString, sqlOptions =>
    {
        sqlOptions.MaxPoolSize(200);
        sqlOptions.MinPoolSize(10);
        sqlOptions.ConnectionIdleTimeout(TimeSpan.FromMinutes(5));
    }));

// Kestrel 线程池配置
builder.WebHost.ConfigureKestrel(options =>
{
    options.Limits.MaxConcurrentConnections = null;  // 无限制或设置合理值
    options.Limits.MaxRequestBodySize = 104857600;  // 100MB
});
```

```yaml
# docker-compose.yml 资源限制
services:
  web:
    deploy:
      resources:
        limits:
          cpus: '2'
          memory: 2G
        reservations:
          cpus: '0.5'
          memory: 512M
```

## 总结

| 性能指标 | 工具 | 常见原因 | 解决方向 |
|---------|------|---------|---------|
| 冷启动慢 | ReadyToRun、Warmup | JIT编译 | 预编译、预热 |
| API响应慢 | MiniProfiler、dotnet-trace | N+1查询、缺索引 | SQL优化、Include/Select |
| 内存增长 | dotnet-dump、dotnet-counters | 泄漏、大对象 | 对象池、流式处理 |
| CPU高 | perf、BenchmarkDotNet | 算法效率、序列化 | 算法优化、缓存 |
| GC频繁 | EventListener | 分配过多 | ArrayPool、减少分配 |
| 并发崩溃 | 连接池监控 | 资源耗尽 | 连接池调优、限流 |

**核心原则**：
1. **先测量再优化**：不要猜测瓶颈在哪
2. **80/20法则**：20%的代码消耗80%的资源
3. **分层优化**：数据库 > 应用代码 > 网络 > 前端
4. **缓存是利器但不是银弹**：注意缓存一致性
5. **定期回归**：性能优化可能引入新bug
